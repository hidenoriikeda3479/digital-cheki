# 03 — 責務分離と通信契約

根拠：DEC-007〜011/018、C08。ここでの設計上の具体化は業務要求の追加ではない。

## 依存方向
```text
Expo Routerの入口 → 画面/表示部品 → 機能の処理
                                    ↓
                        外部サービス・保存のインターフェース
                                    ↓
           組み立て箇所がMock/HTTP・SQLite/FileSystemを選択
```
画面は固定の業務データ、fetch/axios、SQL、保存APIを直接持たない。共通文言・デザイントークンはこの禁止の対象外。
UIと業務処理はMockクラスをimportしない。runtime DTOと表示モデルが違う場合は変換する。
既存構成がこれを満たすなら移動だけの大変更をしない。未実装層を大量に生成せず、機能ごとに追加する。

## 機能単位の契約作成
実装前に以下を記録し、Mockと将来のHTTPで同じ公開インターフェースにする。
- 処理名、目的、関係するFR・画面
- 入力、成功値、エラーコード、null/空一覧、ID・日時・enum
- 認証/役割/グループ/受取人の範囲
- 非同期・取消・進捗・多重呼出し・再実行の意味
- 状態の所有者（端末/仮サーバー/本番API）、コミット完了の時点
- セッション/写真の安定ID、呼出しID、冪等性と結果不明時の照会

API一覧の候補：認証/登録/認証コード/再設定/ゲスト発行/マスタ取得/ファン解決/撮影確定/転送許可/転送状態/受取一覧/通知/問い合わせ/退会。
これは稼働中APIや確定URLの一覧ではない。OpenAPIは必要な機能から追加し、空specを完成扱いにしない。
大きなファイルのバイト転送はHTTPのJSON契約と別でもよい。S3直接転送/ API中継の最終選択は未決で、共通PhotoTransferポート等に閉じ込める。

## 型とエラーの設計案
- IDは不透明な文字列として扱い、ファイル名や連番に意味を依存させない。UUID/ULIDの最終採用は別
- 時刻は境界契約で時差が分かる形式を使う提案。業務比較は統一時刻、表示時だけローカライズ
- エラー分類案：Validation/Unauthenticated/Forbidden/NotFound/Conflict/Expired/Transport/Storage/Cancelled/UnknownOutcome
- 「エラー文にfailedを含む」等で状態判定しない。試行と取消を区別
- 外部JSONは実行時にも検証する。TypeScriptの型だけで受信データの安全を証明しない
- 成功が確定しない送信を単なるfalseに潰さず、照会可能な結果不明として扱う

## スキーマと資料
契約変更はアプリ・Mock・テスト・必要なOpenAPIを同じ変更に含める。既存顧客/APIとの互換性が必要になった段階でversion方針を決める。
設計書は実際に作った責務とコードを記録する。ユーザーのリバースエンジニアリング方針に反して巨大な全体設計を着手条件にしない。
本番API接続時には契約テスト＋異常系結合試験を行う。URL変更だけで完成とは報告しない。
