# 11 — 将来のAPI・AWS（今回構築しない）

確定：C02/C03/C04、DEC-003〜006/019。ここは将来タスク用の制約と設計案。現在のモック依頼でクラウド資源を作る指示ではない。

## 技術と責務
ASP.NET Core Web API＋C#、RDS PostgreSQL、S3、SES、JWT、Expo Notificationsを維持。
APIは認証/認可、グループ・アイドル・会員・ゲスト、撮影、転送許可/状態、期限、通知、問い合わせ、監査を管理。
画像本体はS3、画像ID・キー・所有者・状態・日時・撮影履歴はDB。PostgreSQL→S3へ直列保存する構造と誤解しない。
EF Core＋Npgsqlは提案。採用/.NET/EF/PostgreSQLバージョン、マイグレーション運用は実装前に確認する。
マイクロサービス分割や有料サービスを「大規模だから」で追加しない。

## APIへの切替
契約を機能単位で一致させ、アプリのhttpアダプターを実装する。シード値へ都合よくAPIを合わせず、元の入力検証・所有範囲を維持する。
写真送信はJSONメタデータ処理とバイト転送、完了確定を分ける。S3直接/中継は未決。署名URLに長期鍵を含む設定をアプリへ置かない。
再送は安定IDとサーバーの一意性/状態検証で防ぐ。同じリクエストの再受信を安全に扱うことと、写真再アップロードを許可することは別。
DB更新とS3操作は分散した処理として、途中失敗/重複イベント/最終確認を設計する。
通知もDBの記録と外部配信を同一トランザクションと仮定しない。outbox等は将来の設計候補。

## 写真の7日間保管（外部確認E08/E09）
アップロード完了時刻を正とし、API側でexpiresAt以降の取得を拒否する。端末時計を権限判断の唯一根拠にしない。
S3 Lifecycleの自動削除は非同期で、日数計算に日付境界がある。正確な取得期限と物理削除の達成方法を分ける。
Versioning、delete marker、旧version、複製、ログ/バックアップに写真が残る場合を確認する。1週間後の「破棄」を単なる現行キー非表示で済ませない。
署名URLは期限内に再利用できる性質がある。一度アップロードしたオブジェクトの上書き/再送禁止は別制御が必要。
削除/失効したアカウントが既発行URLで取得できる期間を評価し、即時停止要件の範囲をユーザーと確認する。

## 環境・運用
開発と本番を分け、DB/S3/SES/通知token/アプリID/権限/秘密情報を混在させない。会社PCのモックを本番環境にしない。
AWSアカウント分離やStaging常設は未決。仮の料金試算から勝手に作成しない。
RDSのバックアップ、復旧試験、API監視、期限処理監視は本番の設計対象。機器/回線故障とプログラム不具合を区別する。
JWT有効期間・refresh失効・本人確認・メール送信元を先に合意。ハッシュ化とTLS等の原文要件を守る。
SESメールの文面/再送は合意した認証フローへ接続。本物のパスワードを復元して通知する構造は作らず、初期アカウント通知の安全な運用は別途確認する。
