# 01 — 仕様・根拠・変更の管理

根拠：R1/R2、C05〜C20。外部の読込仕様はE01。根拠コードは[資料一覧](../../docs/source-index.md)。

## 判断する順序
1. 今回ユーザーが明示した対象・変更・禁止事項
2. `docs/decisions.md`の明示的な決定（原文を変更した範囲だけ）
3. R1要求定義の対象ID・受入条件
4. 承認済みの具体化・仮仕様。仮値は本番確定としない
5. 今回のエージェント規約・設計案

これは業務資料間の判定方法であり、実行環境の上位の安全指示やツール権限を上書きしない。
本文の新旧を日付だけで判断しない。「提案した」「ユーザーが了承した」「実機で確認した」を別に追う。

## 分割ファイルの読込
ルートAGENTSを入口とし、変更先の階層別AGENTS、関連するrules、該当FRを読む。リンク先すべての自動読込を仮定しない。
同階層のAGENTS.override.mdは通常AGENTSを隠す可能性がある。既存override、生成済みExpo指示、グローバル指示を確認し、矛盾を報告してから統合する。
詳細資料全体を毎回注入せず、対象の機能・境界・受入に必要な箇所を読む。作業対象を移したら追加の指示を読み直す。

## 原文保存と補足
- requirements.mdとsource-archiveの原文を、誤記修正の名目で無断編集しない
- 旧仕様R2のBluetooth/サーバー画像なし/詳細会員登録/ゲスト移行は現行にしない
- R2にしかない活動終了・プロフィール寸法・共有ルール等は補助資料。必要な範囲を確認して採否を決める
- Cで明示された変更（1アプリ、AWS再確定、iPhone先行等）は旧アシスタント提案より優先する
- 別プロジェクトのWeb配色、教室ロゴ、メール、LINE、コメントの細かな文体規約を混ぜない
- コードコメントは意図・制約を簡潔に書く方針とするが、「ですます禁止」「句点禁止」が当アプリで承認済みとは扱わない

## 不一致への対応
`docs/open-questions.md`に、原文の箇所、関係する発言、影響、仮対応、確認期限を記録する。
誤記候補：目的3、未決合計14対明細6、A-007/A-008、G-002再設定導線、簡略遷移図の抜け。
原文の図をそのまま唯一の実装根拠とせず、機能要件・画面表と照合する。ただし独断で図の原本を訂正しない。

## 完了報告の根拠
要件ID、変更ファイル、確認コマンド、成否、実機確認者を残す。資料の網羅と実装の網羅を区別する。
52件のP1要件を対応表へ載せても、52件の実装が完了した意味にはならない。
取得できていない別チャットの独自の決定は追加しない。会話検索の抜粋と全文精読を混同しない。
