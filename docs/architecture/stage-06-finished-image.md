# 段階06 完成画像と送信前確認

対象：P1-IMG-001/002/003、G-008の画質設定とG-010の送信前確認。アップロード・外部配布は実装しない。

`FinishedImageService.prepare(credential, intakeId)`はグループ権限、受付の受取人1人・参加アイドル1人以上、採用写真1枚以上を確認し、各写真の最新`PhotoEdit`から完成JPEGを順番に作る。成功時は写真ID、編集revision、画質、実寸、実バイト数、端末内参照、生成日時を返す。`confirm`は全採用写真に最新revision/画質の完成ファイルが存在する場合だけ、送信対象を端末内で固定する。これは送信成功・サーバー保存を意味しない。`isConfirmed`は確定状態の照会。受付/写真がない場合はNotFound/Validation、古い編集・参加者変更はConflict、画像/DB/容量の失敗はStorage。受取参照は内部照合に限り、画面には「確認済みの受取人 1人」と表示する。

DEC-059後の現行送信確認では、内部受取参照を画面に出さず、グループ認証と保存済み受付IDを検証する`IdentificationService.getIntakeRecipientName`から会員名（ゲストは「ゲスト」）を取得して`SendPreview.recipientLabel`へ入れる。参加アイドルは当該受付の選択済みIDから表示名を解決する。名前を確認できなければプレビューを成功扱いにしない。上段の匿名表示は段階06当時の仕様。

段階06時点のG-010 UIは「確定して送信する」の1回の押下で`confirm`成功後にG-011の`observe`を行い、その時点で未送信の写真だけに`start`を実行する設計だった。現在はDEC-029/040によりG-007の確認ダイアログで完成画像・枚数・受取人・参加アイドルを表示し、確認後に受付単位で確定・一括送信する。キャンセルでは確定・転送しない。確定失敗・観測失敗時は転送しない。画面再表示や起動では自動送信しない。確定と仮サーバー保存は別の処理・記録であり、UIが連続操作でも原子的成功とは表示しない。

プレビューと出力は同じ`composition-geometry.ts`を使う。Skiaの画面外CPU Surfaceには写真、白背景と枠、保存済みの線・スタンプだけを描き、UIのボタンやツールバーは含めない。元写真バイトは端末内のFileSystemラッパーから読み、完成JPEGを`document/digital-cheki/<環境>/<source>/group/<id>/finished/`へ一時保存・検証してから確定する。SQLiteのグループ別`finished-intake/<intakeId>`にはschemaVersion 1と写真ごとのrevision/画質/相対参照/実寸/バイト数を保存し、画像バイトや編集JSONは入れない。JPEGは符号と画像ヘッダーから形式・実寸を再検査する。再起動時はファイルと記録が一致する場合だけ再利用し、欠損や編集世代変更は再生成する。ファイル保存とDB更新を原子的とみなさず、DB失敗後に残った同世代ファイルを確認して再記録できる。元写真・編集記録は保持する。

生成は1枚ずつ行い、グループごとの端末内操作ゲートで撮影・編集・確定と順序を合わせる。ログアウト後の遅い結果は元グループの領域にのみ残り、別利用者の画面に出さない。端末内確定後の追加撮影、不採用削除、編集はサービス境界でも拒否する。写真・対象集合の固定はOPEN-016/022に対するモックでの安全な仮運用であり、本番の再編集/再配布ルールは未合意。送信APIへ引き渡すのは将来この完成JPEGと固定された写真IDで、元写真と編集JSONは対象外。

DEC-033後の出力は`cheki-format.ts`のinstax mini外枠54:86で統一し、白枠ありは写真窓46:62を中央寄りの上4 mm位置へ配置する。標準の長辺1600px・高画質3000px、JPEG圧縮品質82/88、上下余白配分はOPEN-002の仮値。容量・枚数上限は設けない。画質・容量・処理時間・構図の一致はiPhoneで測り、OPEN-002を解消扱いにしない。Android表示/保存も未確認。

`FinishedImageService.getSaved`はグループ所有・最新編集世代・ファイル実体を確認し、端末に保存済みの完成画像だけを読み出す。G-007/G-013の表示に使い、編集更新後の旧JPEGは返さない。旧出力との衝突を避けて新ファイル名に`v2`を付け、未確定の旧JPEGは新寸法で再生成する。送信確定済みの旧JPEGは旧名のまま読み、履歴と仮サーバーの内容を無断で変更しない。編集完了時に`prepare`でファイルとDBを確定し、保存成功まで編集画面を閉じない。

自動試験はSkia/CanvasKitで実際のJPEGを生成し、1600/3000px、写真画素・白枠・線・スタンプの画素を確認する。Nodeの実SQLite/ファイル再オープンで完成ファイルとメタデータの一致、編集後の再生成、部分失敗・DB失敗・容量不足からの再試行、0枚/古い編集/確定後の変更拒否を確認する。Expo Go実機のNative Skia/FileSystemと性能は別試験。
