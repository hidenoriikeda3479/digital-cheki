# 段階08 仮受信・アルバム契約（2026-09-25）

対象は P1-DWN-001〜005、P1-ALB-001/004 のモック経路。実API、別端末同期、通知一覧、検索、お気に入り、OS写真アプリ保存は対象外。

## 呼び出しと所有範囲

- `DownloadService.list(credential)` は認証済みファン自身の内部受取参照を `IdentificationService.getOwnRecipientRef` で解決する。仮サーバーの完了済み撮影通知に載った写真だけを返す。グループ側のローカルファイルURIは返さない。
- `DownloadService.download(credential, intakeId, photoId, onProgress)` は毎回、受取参照・撮影ID・写真ID・通知済み範囲・仮サーバー期限を検証する。UIのボタン操作からのみ呼ぶ。失敗後の自動再試行はない。
- `PhotoReceivePort` は仮サーバーの完成JPEGをファン別の端末領域へコピーする。`mock-server/.../uploads/upload-<photoId>.jpg` と `fan/<fanId>/received/received-<photoId>.jpg` は別ファイル。受信中は `.pending-...` に書き、サイズ検証後に完成名へ移す。
- ファン別SQLiteキーは `fan/<fanId>/download/photo/<photoId>`。`schemaVersion: 1` と状態・進捗を記録する。端末内の元ファイルとDBは単一トランザクションではない。`receiving` の再読込で完成ファイルとサイズが一致すれば受信完了へ復旧し、未完成なら失敗として手動再受信を待つ。途中ファイルはアルバムへ出さない。
- `unreceived / receiving / failed / received / expired` を表示する。受信済み端末ファイルは仮サーバー期限後も表示し、未受信は期限後に取得を拒否する。ファン切替時、コントローラーの世代番号で前アカウントの遅い画面応答を捨てる。
- アルバムは受信済みの端末ファイルだけを `capturedAt` の降順で表示する。新たなアップロード記録には段階04の撮影日時を含める。段階07で作成済みの古い記録に撮影日時がない場合だけ `uploadedAt` で代替表示し、旧データの正確な撮影順は未検証。
- F-007の写真一覧へ入る際は`DownloadController.open`が取得を終えるまで元画面を維持し、ファン別一覧と通知が揃った状態で画面を切り替える。前回の一覧や暫定空一覧を読込中に見せない。再読込の進捗表示はグリッド上へ重ね、縦方向のレイアウトを変更しない。

## 未決と仮運用

- OPEN-018: 期限内に開始して転送中に期限へ達した場合、今回のモックは開始時点の許可で処理を続ける。公開仕様・実API/S3の境界動作は未決。期限後の新規開始は拒否する。
- OPEN-021: 受信状態とファイルはこの端末のファン別領域だけに保存する。他端末へ受信済みを伝播しない。別端末の受信事実の管理単位は未決。
- 開発モックの途中失敗設定は次の明示受信操作にだけ作用し、保存済みの写真や本番コードの成功判定を変更しない。

## 試験の範囲

Native APIのJest代替で、実ファイルコピー、実SQLite再オープン、3枚受信、別ファン遮断、途中失敗と手動再受信、7日境界、ファイル確定後のDB中断復旧、画面ボタンとログアウト中の遅延応答を確認する。iPhone Expo Goの実ファイル・表示・強制終了試験は別途必要。

## DEC-042 受信済み写真の複数選択（2026-09-26追記）

上記の段階08当時の対象外記述から、ユーザーの追加指定により写真アプリへの書き出しを追加した。F-007の受信済み写真だけを複数選択する。`LocalAlbumActions.requestSavePermission`は写真追加権限を一度確認し、`saveToPhotoLibrary(credential, intakeId, photoId)`は毎回受取人・撮影ID・写真ID・ローカルファイルの存在を検証してから`DevicePhotoLibrary.save`へ渡す。OS側はExpo SDK 57の`Asset.create`を使い、アプリ内の原本は維持する。途中失敗時、成功した枚数を示し、残りだけを選択状態に残す。

`deleteReceived`は確認後にファン別の受信ファイル・お気に入り・受信状態を更新する。仮サーバー画像・送信履歴・他の利用者のファイル・写真アプリへの書き出し済みコピーには作用しない。ファイル削除とSQLite記録が同時成功するとは扱わず、途中失敗ではエラーと再読込時の状態を確認する。OS写真アプリへの保存は複数ファイルの一括トランザクションではなく、失敗時に既に保存されたコピーは維持する。

## DEC-044 受信完了後の再受信禁止（2026-09-26追記）

受信完了は受取人別の永続台帳で保持する。受信済み写真の二度目の`download`は期限内でも`Conflict`を返し、アプリ内コピーを削除したら台帳を`removed`として残す。`removed`は未受信一覧・件数から除き、撮影単位の履歴には「端末から削除済み・再受信不可」と表示する。以前の実装で削除時に明示保存された`unreceived`行は`removed`へ移行する（初回の未受信写真には行がない）。受信済み行のファイルが欠けた場合も再受信可能へ戻さない。受信失敗で完了していない写真の手動再試行は維持する。複数端末での判定共有はOPEN-021のまま、本番API側に永続的な受信事実と再受信拒否が必要。

## DEC-061 未受信プレビューと一括受信（2026-09-27追記）

`DownloadService.list`の写真に任意の`previewUri`を返す。モックは仮サーバーが受取参照・撮影ID・写真ID・期限・ファイルサイズを検証した後だけ、同一端末内の完成JPEG参照を返す。画面は仮サーバーの保存パスを組み立てない。表示だけではファン領域へコピーせず、受信台帳も完了にしない。期限切れ・ファイル欠落時はプレビューなし。実API側の画像配信・認可方法は未実装であり、モックの`file://`参照をHTTP契約と確定しない。

F-008右上の一括受信は未受信・受信失敗写真に対する1回の明示操作。既存の`DownloadService.download`を順番に各写真へ1回呼び、部分失敗後も次の対象を処理して最後に状態を再取得する。起動・更新ボタンでは転送しない。受信済み・期限切れ・削除済みは対象外で、失敗分は別の手動操作まで再試行しない。画面の撮影日・期限は日付だけを表示する。

## DEC-068 受付単位の受信操作（2026-09-27追記）

F-008は`intakeId`ごとに1カードを表示し、受信可能な写真に対して1つのボタンで`DownloadController.receiveIntake(intakeId)`を呼ぶ。右上の一括受信は受付を順に処理する。画面から写真別の受信操作をなくし、ホーム右上の件数は受信可能な受付数とする。受付の中の複数JPEGは既存の`DownloadService.download(credential, intakeId, photoId)`を順番に呼び、受取人・写真ID・期限・端末ファイル・SQLite記録は引き続き写真別に検証する。これは単一ファイル転送や原子的な一括保存を意味しない。途中失敗では残りも処理し、成功済みを再転送せず、次の明示操作で未完了分だけを試みる。期限切れ・削除済みの写真は対象外。実APIの受付単位リクエスト方式は未決で、画面から写真別のサービス呼出しは行わない。

## DEC-070の現行UI（2026-10-14）

上記の独立F-008/receive-list UIは履歴。現行はF-007上の受取スタックモーダルへ置き換えた。受付単位の対象確認、全対象・期限・失敗理由、明示受取と手動再試行は維持する。[現行設計と確認手順](home-receive-modal.md)を参照。保存サービス・台帳・認可・期限・復旧はこの段階の契約を継続する。
