# 段階10：会員登録とゲスト開始の契約・仮運用

対象は P1-FAN-001/002/004 と P1-GST-001/002/003、F-002/003/005/006。会員登録の呼び出し口は `EnrollmentService`、認証は既存の `AuthService`、相手照合は `IdentificationService`、受信は既存の `DownloadService` を使う。公開用のAPI URL・メール配信契約は未定。

## 会員登録

`requestRegistration({email, displayName, password})` は `requestId/email/expiresAt` を返す。画面が受け取る契約にコードは含めない。`resendCode(requestId)` は新しいコードを発行し旧コードを無効化する。`verifyCode(requestId, code)` は6桁の文字列を照合し、期限は `now < expiresAt` の時だけ有効として会員セッションを返す。誤コードは `Unauthenticated`、期限切れは `Expired`、不正入力は `Validation`。`Clock` は注入可能。

モック専用受信箱は `MockEnrollmentInbox` に分離し、開発用bundleだけに存在する。実メール、SES、業務HTTP、外部画像URLは使用しない。入力項目はメール、ファン名、パスワードだけ。登録時のパスワード検証は8文字以上、英大文字・英小文字・数字を各1文字以上とし、ログイン時の入力検証には適用しない。

DEC-062：F-003から`MockEnrollmentInbox`の表示ボタンとコード本文を外した。サービスのモック受信箱は自動試験用に残り、アプリ画面へコードを渡さない。期限表示は`expiresAt`を端末の現地時刻の`yyyy/MM/dd hh:mm:ss`（24時間）へ整形する。実メール未接続の現状ではiPhone画面からコードを取得できないため、新規会員登録の実機完走はOPEN-031として未確認にする。

モック仮サーバーの登録待ち状態にはソルトとSHA-256ダイジェスト、コード、期限を保存し、パスワード平文は保存・ログ出力しない。これはモック検証用であり、本番のパスワード保管方式ではない。初期fixtureの `DemoPass123` は既存の別経路を維持する。認証成功後、受取人台帳に会員を作成して認証台帳へ登録する。別々の永続記録のためリトライ時に同じ内部IDを使い、受取人重複を避ける。片方の書き込みだけが成功した場合にモック台帳へ到達不能レコードが残り得るため、本番APIではサーバー側の原子的な登録が必要。

既存のグループ用・削除済み・登録済みメールと重なる場合は登録を保留する。役割重複と削除済みメール再利用は OPEN-004/005 のまま。仮登録中に同じメールで再申請すると、新しい申請に置き換えて旧コードを無効にする。メール長・ファン名長や正規化の本番上限は未合意。

## ゲスト

`startGuest()` は会員とは異なる内部IDとSecureStoreに保持する再開用の不透明なキーを発行する。受取人台帳にはゲストQRと6桁の番号を同じ受取参照で保存する。QR/番号はグループによる相手照合用でありログイン権限にはしない。同じ端末のグループ切替後、`resumeGuest()` はSecureStoreのキーから新しいモックセッションを発行する。ログアウトは写真やこの再開キーを削除しない。最後に開始したゲストだけをこの端末から再開する仮運用で、複数ゲスト・別端末復元・番号再発行は未実装。

DEC-056：ログイン画面の「ゲストで始める」は `resumeGuest()` を先に呼び、保存情報がない場合だけ `startGuest()` を呼ぶ。取得したセッションを保存して直接ゲストホームへ進み、F-006のQR/番号はホームの「受付」から開く。ゲスト開始専用画面は使わない。再開処理が失敗した場合は自動で別ゲストを作らない。新規発行・再開とも認証情報の端末保存が成功してから保護画面を出す。

ゲストの受信記録と完成画像コピー先は `guest/<id>` 名前空間。会員の `fan/<id>` と分け、撮影時の内部受取参照も移行しない。会員登録後のゲスト写真・履歴の付替えを行わない（DEC-022）。モック一時番号は未使用の6桁文字列を選び、先頭0を保持する。現段階のモックは期限・再発行を行わず、台帳内で重複を避ける。これは OPEN-020 の仮値であり、本番の寿命・衝突・移行方針の決定ではない。
