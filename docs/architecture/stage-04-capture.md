# 段階04 撮影・端末保存の契約

対象：P1-SHT-002/003/004、P1-REC-001/002の撮影部分。G-002/G-006/G-007。落書き・送信は今回含まない。

現行DEC-043：送信前に中断した受付のユーザー向け復旧は行わない。ログイン時に旧受付・撮影中一覧を読まず、ホーム/端末写真管理から再開・送信する導線を外す。受付内で動作中の写真保存とファイル/DB整合性確認は続ける。送信確定後の転送失敗・結果不明は再照会/明示再送を維持。既存の送信前ファイルは自動削除せず、整理方法はOPEN-030。以下の復旧記述は段階04当時の契約として残す。

`CaptureService` は認証済みグループのcredentialと既存の`CaptureIntake.id`を毎回検証する。`savePhoto`の入力はカメラの一時URI、縦横ピクセル数、返却画像形式（jpg/png）で、成功値は安定した写真ID・撮影時刻・元画像/縮小画像の相対参照。`listPhotos`は受付内の採用中写真だけ、`discardPhoto`は指定写真を不採用として数・後続送信対象から除外する。`listSessions`は自グループの未完了受付と採用写真枚数・復旧要確認状態を返す。別役割・別グループはForbidden、無効セッションはUnauthenticated等、保存・容量不足・参照欠損はStorage、重複IDはConflict。カメラ・端末保存はローカル処理で、業務外部通信しない。

DEC-041の画面導線：G-002右上の独立した撮影受付一覧画面は使用しない。`listSessions`の未完了受付をグループホーム内に表示して再開し、確定済み写真の閲覧はG-013端末写真管理に残す。受付データや復旧処理は削除しない。

SQLiteの既存KeyValueStoreにグループ別の`capture-photos`をschemaVersion 1で保持する。写真の状態は`copying`→`ready`、不採用時は`discarding`→記録除外。最初にIDと一時URI・期待バイト数・寸法を記録し、FileSystemのグループ領域へ元画像を一時コピーしてサイズ確認、確定後に縮小画像を作る。両ファイルを確認してからDBを`ready`にする。ファイルとDBを単一トランザクションとは扱わない。再起動時の照会は`copying`の一時URIまたは確定ファイルを検査して復旧し、欠損・不一致を採用枚数に含めない。`discarding`は対象ファイルの削除を再試行する。写真ID・受付IDは再起動しても変えない。

元画像と縮小画像は`document/digital-cheki/<環境>/<source>/group/<id>/`配下へ分ける。DBには絶対URIを永続保存せず、写真IDから同じ名前空間の相対参照を解決する。縮小画像の長辺320pxは一覧性能の実装値で、完成画像の画質仕様ではない。Cameraの`skipProcessing`は使わず、端末の向き調整済みの静止画を保存する。容量の業務上限・自動削除しきい値は設けない。保存時の空き容量不足は警告し、利用者の採用写真を自動削除しない。

撮影は1操作ずつ行い、保存完了まで再押下を止める。保存結果が不明な失敗後は続けて撮らせず、ホームから受付を開き直して復旧結果を照会する。途中でログアウトしても処理の保存先は開始時のグループに固定し、後から届いた結果は別利用者の画面へ反映しない。不採用は送信確定前の明示操作のみ。現段階では送信確定処理自体を実装しない。OPEN-002/023の本番画像品質・外部写真アプリ保存は未決のまま。

現在の画面導線ではG-007の撮影写真一覧から写真を押すと直接G-008/G-009の編集へ進む。独立した写真詳細確認画面は使わない。不採用確認・削除は一覧の写真ごとに操作する。

DEC-033〜035追加：G-006はカメラ映像自体を画面へ広く配置し、下部中央の丸い撮影ボタンと写真一覧へ戻る操作だけを重ねる。撮影中はネイティブタブと開発用ボタンを隠し、白枠・補助線・撮影モード・ズーム等は表示しない。`skipProcessing: false`で得た端末画像を中央クロップしてから既存`CaptureService.savePhoto`へ渡す。保存される元画像はinstax mini写真部分46:62の比率で、物理mmの解像度や印刷品質を保証するものではない。画面プレビューは端末の表示比率で拡大されるため、iPhoneで保存画像との画角差を確認する。
